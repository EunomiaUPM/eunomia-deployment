---
title: "Extra participants"
description: "More connectors and authorities next to the standalone deployment, each on its own ports, and how to connect them."
---

Next to the standalone deployment you can start as many extra **connectors** (provider or consumer agents) and **authorities** as you need, for example one per team. Each one:

- gets free ports, HTTP in `1600-1999` and Postgres in `15400-15999` (`EUNOMIA_HTTP_PORTS`, `EUNOMIA_DB_PORTS`);
- is its own compose project, `eunomia-<name>`, with its own containers and volumes;
- gets its own keys, certificate and VAT number, so its own DID, under `instances/<name>/`;
- has its configuration generated from the standalone one, with its own port.

Wherever a command takes a participant, `consumer`, `provider` and `authority` are the standalone ones.

## Create

```bash
./eunomia connector add                              # a consumer called conn-xxxx
./eunomia connector add seller --role provider       # a provider called seller
./eunomia connector add buyer --onboard              # and register it with the standalone authority
./eunomia connector add buyer2 --authority my-auth   # register it with another authority
./eunomia authority add my-auth                      # a Heimdall (--role eco, the default, or dataspace)
```

Names are lowercase letters, digits and dashes, starting with a letter.

## Onboard and connect

```bash
./eunomia register seller                            # DataSpaceParticipant from the standalone authority
./eunomia register buyer --authority my-auth         # from another authority
./eunomia gaia --consumer buyer --provider seller    # Gaia-X credentials for buyer, then connect it to seller
./eunomia connect buyer seller                       # only the connection, if buyer already has them
```

Providers ask consumers for `gx:LabelCredential`. `connect` without it stays `Pending`, and the CLI says so: get it with `gaia`, from an authority with the eco role.

## Share data between them

```bash
./eunomia catalog populate --provider seller         # the demo factory dataset, offered by seller
./eunomia e2e --consumer buyer --provider seller     # negotiate, pull and push between them
./eunomia demo events --consumer buyer --provider seller
```

Every provider populated this way offers the same demo factory. To offer something else, see [Extending the deployment](/docs/guides/extending).

## Inspect and remove

```bash
./eunomia instances            # every instance, its ports and state
./eunomia status seller        # its containers and URLs
./eunomia logs seller -f       # its logs
./eunomia stop seller          # stop it, keeping its data
./eunomia start seller         # start it again
./eunomia rm seller            # remove its containers, volumes and configuration
```

`./eunomia status` also lists the instances after the standalone stacks.

`./eunomia down` leaves the instances alone, but it wipes the databases of the standalone participants, which then forget the instances while the instances still remember them. If an instance worked with the standalone authority, provider or consumer, remove it and create it again after a `down`.

## What is in instances/name

| File | What |
| --- | --- |
| `instance.env` | name, kind, role and ports: the registry the CLI reads |
| `config/agent.yaml` or `config/authority.yaml` | the generated configuration |
| `config/fafnir.yaml` | the wallet configuration |
| `vault/` | its keys and certificate, and what the setup jobs derive from them |

The compose templates are in [`deployment/instances/`](https://github.com/EunomiaUPM/eunomia-deployment/tree/main/deployment/instances). Inside an instance's project the services are called `db`, `redis`, `wallet` and `agent` (or `heimdall`), and the containers `<name>`, `<name>-db`, `<name>-wallet`…
