---
title: "Standalone deployment"
description: "Every participant and the demo factory on one machine, and how to run, inspect and reset it."
---

The standalone deployment runs the authority, the provider, the consumer and the demo factory on one host. Secrets use a file vault, identities are `did:jwk`, and nothing needs a domain, TLS or an external service. It is the default of every `eunomia` command.

## Lifecycle

```bash
./eunomia up                 # start, wait, onboard, populate the catalog
./eunomia up provider demo   # only some stacks
./eunomia status             # containers, health and readiness; non-zero exit if a node is not ready
./eunomia logs provider -f   # follow one stack's logs (authority, provider, consumer, demo)
./eunomia stop               # stop, keeping data and identities
./eunomia down               # remove containers, networks, volumes and generated identities
```

`down` asks first. `--dry-run` shows what it would remove, `--keep-identities` keeps the generated keys in `vault/` so the agents keep their DIDs, and `--yes` skips the question.

`up --no-onboarding` only starts the stacks, `--no-catalog` skips the catalog, `--pull` pulls the pinned images first, and `--build` rebuilds the demo factory image.

## The stacks

Each participant is its own compose project, with its own network:

| Compose file | Project | Containers | Configuration |
| --- | --- | --- | --- |
| `deployment/standalone/docker-compose.standalone.heimdall.yaml` | `eunomia-authority` | Heimdall, Fafnir wallet, Postgres | `static/config/heimdall/standalone/standalone.eco_authority.yaml` |
| `deployment/standalone/docker-compose.standalone.provider.yaml` | `eunomia-provider` | DS-Agent, Fafnir wallet, Postgres, Redis | `static/config/provider/standalone/standalone.provider.yaml` |
| `deployment/standalone/docker-compose.standalone.consumer.yaml` | `eunomia-consumer` | DS-Agent, Fafnir wallet, Postgres, Redis | `static/config/consumer/standalone/standalone.consumer.yaml` |
| `services/demo-factory/docker-compose.yaml` | `eunomia-demo-factory` | static API, dynamic API, Postgres, Keycloak and its Postgres | |

Every container is named `eunomia-*` (the prefix is `EUNOMIA_PREFIX`). Inside a project the services reach each other by service name (`provider-db`, `provider-redis`, `provider-fafnir-wallet`); between projects, through the host at `host.docker.internal`. The wallets publish no port.

Each stack also has one-shot `*-setup` containers that prepare the database and the keys and then exit: `exited` is their normal state.

### By hand

To drive Compose yourself, pass `versions.env` and start them in this order, then onboard:

```bash
for f in heimdall provider consumer; do
  docker compose --env-file versions.env -f deployment/standalone/docker-compose.standalone.$f.yaml up -d --wait
done
docker compose --env-file versions.env -f services/demo-factory/docker-compose.yaml up -d --wait
./eunomia onboard
./eunomia catalog populate
```

From another container, every participant is at `http://host.docker.internal:<port>`.

## State

- **Databases**: catalog, agreements, transfers, credentials and the wallet state. They live in Docker volumes: `stop` keeps them, `down` removes them.
- **Identities**: the keys and certificates in `vault/<participant>/secrets/`, through a bind mount. The committed `*.pem.example` files are the participants' keys; the setup jobs derive the `*.json.example` files from them. `down` removes the derived ones unless `--keep-identities`.

After a `down`, the next `up` starts from nothing: new wallets, new credentials, an empty catalog that `up` populates again.
